# AlmatyLISPollingBot Requirements

## 1. Цель документа

Этот документ описывает требования к проекту `AlmatyLISPollingBot`.
На первом этапе по нему должна быть создана заготовка проекта без реализации бизнес-логики:

- каркас решения на C# 10;
- слои по clean architecture;
- основные интерфейсы и точки расширения;
- инфраструктурные проекты;
- конфигурация приложения;
- заготовки под миграции, health checks, тесты и контейнеризацию.

Детальные DTO на этом этапе можно не фиксировать.

## 2. Назначение проекта

Бот помогает админам Telegram-чата выбирать турниры на ближайшую субботу через опрос и готовить итоговый пост для Telegram-канала.

Основной сценарий:

1. Админ запускает опрос командой `/poll` в общем чате.
2. Бот получает список подходящих турниров из API `api.rating.chgk.info`.
3. Бот фильтрует и сортирует турниры.
4. Бот публикует в чат сообщение со списком кандидатов и затем Telegram poll.
5. В заданное время или по команде `/stop` опрос завершается.
6. На первом этапе публикация в канал автоматически не выполняется.
7. Для ручной подготовки поста в будущем используется helper-команда в личке `/makepost id1,id2`.

## 3. Технические ограничения и стек

- Язык: `C# 10`
- Архитектурный подход: `Clean Architecture`
- Telegram library: `Telegram.Bot`
- База данных: `PostgreSQL`
- Режим работы бота: `long polling`
- Часовой пояс приложения по умолчанию: `Asia/Almaty`
- Конфигурация должна поддерживаться через `.env` и переменные окружения контейнера
- Приложение должно запускаться в Docker-контейнере
- Целевая среда размещения:
  `Orange Pi Zero 3`
  с `Ubuntu Server`
  (`Orange Pi 1.0.6 Noble`, `Ubuntu 24.04`, `noble`)

## 4. Контекст использования

- Бот работает только с одним Telegram-чатом.
- События из других чатов должны игнорироваться; интеграция с Telegram-каналом в текущей реализации отсутствует.
- Команды доступны только администраторам.
- На команды от не-админов бот не реагирует.
- Бот добавляется в чат администратором Telegram.

## 5. Пользователи и права

### 5.1 Роли

- `Chat admin`:
  может использовать команды в общем чате;
  определяется как администратор Telegram-чата;
  также кэшируется в БД.
- `Main admin`:
  получает критические уведомления в личные сообщения;
  его `Telegram user id` задаётся через `.env`.

### 5.2 Правила доступа

- Доступ к командам в чате имеют только администраторы чата.
- Кэш администраторов хранится в БД.
- Кэш администраторов синхронизируется из Telegram раз в неделю:
  каждый понедельник в `06:00` по `Asia/Almaty`.
- Если Telegram позволяет ограничить меню команд только администраторами, это нужно поддержать.

## 6. Первый этап реализации

На первом этапе должны быть заложены:

- команда `/poll`;
- команда `/stop`;
- инфраструктура для будущих команд в личке;
- модель настроек;
- модель хранения истории и состояния опроса;
- интеграция с API турниров;
- каркас для ручного формирования поста `/makepost`.

На первом этапе не требуется реализовывать:

- автоматическую публикацию в канал;
- реальные команды администрирования в личке;
- расширенные сценарии single-choice poll;
- аргументы команды `/poll`.

## 7. Источник данных о турнирах

Источник: `https://api.rating.chgk.info/#tag/Tournament/operation/api_tournaments_get_collection`

Бот должен уметь:

- получать турниры на целевую дату;
- повторно запрашивать данные перед ручным созданием поста;
- обрабатывать ошибки API;
- при критических ошибках отправлять уведомление `main admin`.

## 8. Логика определения даты

- Основная команда запуска: `/poll`
- По умолчанию команда создаёт опрос на ближайшую субботу в часовом поясе приложения.
- Таймзона задаётся в конфигурации.
- В будущем должны быть предусмотрены расширения команды аргументами, но на первом этапе они не реализуются.

## 9. Отбор турниров

### 9.1 Обязательные фильтры

Турнир должен проходить через следующие условия:

- `type` равен `3` или `6`
- в будущем должно быть легко добавить `type = 8`
- есть русский язык
- `ggRating = true`
- `dateStart` и `dateEnd` попадают в допустимые рамки субботнего отыгрыша
- турнир не находится в списке заранее исключённых `tournament id`

### 9.2 Сортировка

- Основная сортировка: по `difficultyForecast` по убыванию
- При отборе берутся первые 9 турниров после сортировки

### 9.3 Недостаточное количество кандидатов

- Если после фильтрации найден только 1 турнир, опрос не создаётся.
- Если подходящие турниры не найдены, опрос не создаётся.
- В обоих случаях бот должен отправить уведомление `main admin`.

## 10. Публикация списка и опроса в чат

Перед созданием poll бот должен:

- отправить сообщение со списком доступных турниров;
- при необходимости поддержать пагинацию списка;
- затем отправить сам Telegram poll.

### 10.1 Ограничения по вариантам

- В poll должно быть не более 10 вариантов всего.
- До 9 вариантов занимают турниры.
- Последний вариант:
  `"посмотреть результаты"`.
- Если турниров меньше 9, последний вариант всё равно должен быть `"посмотреть результаты"`.

### 10.2 Правила голосования

- Основной режим: `multiple choice`
- Каждый выбранный турнир получает `+1` голос от пользователя.
- Вариант `"посмотреть результаты"` не участвует в выборе победителей.
- Для подсчёта достаточно финального состояния результатов опроса.

## 11. Завершение опроса

Опрос должен завершаться:

- автоматически в фиксированное время;
- вручную по команде `/stop`.

Требования к времени остановки:

- время хранится в настройках;
- настройка должна быть предусмотрена как будущая команда в личке;
- используется часовой пояс приложения `Asia/Almaty`.

Повторный запуск `/poll` допустим:

- если уже есть активный опрос, новый запуск должен остановить предыдущий и создать новый.

## 12. Определение результатов

Целевой результат стандартного сценария: выбрать 2 турнира.

### 12.1 Правила выбора

- Победители определяются по числу голосов.
- Используются `top-2` турнира.
- Более популярный турнир считается первым.
- Менее популярный турнир считается вторым.

### 12.2 Неоднозначные результаты

Результат считается неясным, если:

- есть деление `1-2` мест;
- есть деление `2-3` мест.

При неясном результате:

- автоматические действия по публикации невозможны;
- допускается только ручной режим.

### 12.3 Отсутствие голосов

- Если голосов нет, бот всё равно завершает опрос.
- Дополнительных действий после завершения не требуется.

## 13. Ручное формирование поста

На первом этапе нужно заложить фичу ручного создания поста в личке с ботом:

- команда: `/makepost id1,id2`
- вход: два `tournament id`, переданные через запятую
- перед формированием поста бот повторно получает данные по турнирам из API

### 13.1 Правила формирования поста

- В посте всегда 2 турнира.
- Первый турнир ставится на слот `13:00`.
- Второй турнир ставится на слот `15:30`.
- Более популярный турнир должен идти первым.
- Место проведения хранится в БД как настройка.
- Шаблон поста один.

### 13.2 Пример формата поста

```text
❓ Что: «Синхрон Олимпийского кубка Беларуси — часть 2» (Хаиткулов Р.Г., Колесов А.А., Разумов Ю.В., Скиренко А.С.)
📍 Где: "Tamos Education", Абиша Кекилбайулы, 129/4
🗓 Когда: суббота, 21 февраля, 13:00.
⏳ Дистанция: 36 вопросов (5,0 trueDL).
💵 Стоимость: 900₽ (~5800₸) с команды.

❓ Что: «Серия Premier. F - значит февраль» [казлига/оазис] (Мерзляков М.П., Сахаров Д.А., Мухаметкалиев А.С.)
📍 Где: "Tamos Education", Абиша Кекилбайулы, 129/4
🗓 Когда: суббота, 21 февраля, 15:30.
⏳ Дистанция: 36 вопросов (4,5 trueDL).
💵 Стоимость: 900₽ (~5800₸) с команды; 600₽ (~3900₸) студенты; пары - 500₽ (~3200₸); школьники и соло - 300₽ (~2000₸).

❗️ Представительство и ведение оплачивается отдельно - 5000₸ делится между всеми участвующими командами, за исключением школьных
```

## 14. Будущие функции, которые нужно заложить архитектурно

Нужно предусмотреть точки расширения под:

- команды в личке для настройки бота;
- бан `tournament id`;
- снятие бана `tournament id`;
- shadow ban пользователей;
- настройку времени автоостановки опроса;
- настройку места проведения;
- single-choice режим опроса;
- аргументы для `/poll`;
- ручную или полуавтоматическую публикацию в канал.

Названия будущих команд в этом документе пока не фиксируются, кроме `/makepost`.

## 15. Shadow ban

Функция нужна как будущая возможность.

Требования:

- админ сможет в личке добавить пользователя в список `shadow banned`;
- если голос такого пользователя присутствует в финальном результате, он не должен учитываться;
- список `shadow banned user ids` хранится в БД.

На первом этапе можно ограничиться архитектурной закладкой этой возможности без полной реализации.

## 16. Хранение данных

В БД должны быть предусмотрены сущности или таблицы для:

- `chat id`
- идентификатор рабочего чата
- `excluded tournament ids`
- `admin ids`
- `shadow banned user ids`
- истории проведённых турниров
- состояния активного опроса
- `poll message id`
- `poll id`
- настроек места проведения
- настроек времени автоостановки

### 16.1 История проведённых турниров

Для истории требуется хранить минимум:

- `tournament id`
- дата
- время

История на текущем этапе используется только как журнал.

## 17. Конфигурация приложения

Через `.env` или переменные окружения должны настраиваться минимум:

- Telegram bot token
- PostgreSQL host
- PostgreSQL port
- PostgreSQL database name
- PostgreSQL user
- PostgreSQL password
- application timezone
- `main admin id`

Строка подключения к PostgreSQL не должна передаваться одной переменной.
Она должна собираться в коде приложения из отдельных конфигурационных значений.

Допускается расширение списка конфигурации по мере проектирования каркаса.

## 18. Нефункциональные требования

Обязательно предусмотреть:

- структурированное логирование;
- обработку ошибок;
- retry для внешнего API;
- health checks;
- docker-compose;
- миграции БД;
- тестовые проекты;
- учёт ограничений целевой ARM-платформы при контейнеризации и выборе базовых образов;
- удобное расширение функциональности без нарушения границ слоёв.

## 19. Архитектурные ожидания от стартового каркаса

Стартовый каркас проекта должен включать:

- solution с разделением по слоям;
- слой `Domain`;
- слой `Application`;
- слой `Infrastructure`;
- слой `Presentation` или `Worker` для Telegram bot host;
- проекты тестов;
- конфигурацию DI;
- абстракции для Telegram API, внешнего CHGK API и хранилища;
- заготовку планировщика фоновых задач;
- заготовку миграций;
- контейнеризацию.

## 20. Критерии готовности первого этапа

Первый этап можно считать успешным, если:

1. По этому документу можно создать каркас решения без дополнительных продуктовых вопросов.
2. В каркасе уже видны точки расширения под будущие команды в личке.
3. Учтено ограничение одного рабочего чата; публикация в каналы не входит в текущую реализацию.
4. Учтены права администраторов и синхронизация их кэша.
5. Учтены сценарии `/poll`, `/stop` и заготовка `/makepost`.
6. Учтены БД, конфигурация, логирование, health checks и контейнеризация.
