# Возврат турнира из исключений

## Понимание задачи

- Администратор должен иметь возможность вернуть ранее исключённый турнир в пул кандидатов.
- Запись об исключении не удаляется из базы данных.
- Возврат доступен только авторизованному администратору в личной переписке с ботом.
- Команда поддерживает ID и ссылки, разделённые пробелами, запятыми или переводами строк; без аргументов запускается существующий тип личного диалога.
- Невалидный элемент отменяет всю операцию и не меняет базу.
- Повторное исключение возвращённого турнира должно реактивировать ту же строку, а не создавать новую.

## Допущения

- Команда называется `/unexclude`.
- ID, для которого нет активного исключения, считается уже находящимся в пуле; обращение к API CHGK не требуется.
- Одной записи на `TournamentId` достаточно для подтверждения того, что он хотя бы раз был исключён. Полный журнал каждого переключения состояния не входит в эту фичу.
- Требование не менять пользовательский ` requests.md` с незакоммиченными изменениями важнее отметки чекбокса в нём.

## Варианты

1. **Рекомендованный:** добавить `IsDeleted` и `DeletedAtUtc` в существующую запись. Уникальный ID сохраняется, lookup читает только активные строки, а повторное исключение реактивирует строку.
2. Использовать поле `IsActive`. Семантика хуже совпадает с общепринятым soft delete и менее явно показывает момент возврата.
3. Завести отдельную таблицу событий исключения. Это дало бы полный аудит, но потребовало бы дополнительной модели и выходит за рамки текущего запроса.

Выбран первый вариант.

## Дизайн

`ExcludedTournament` получает `IsDeleted` и `DeletedAtUtc`. Миграция задаёт `false` для всех существующих строк, поэтому текущие исключения продолжают работать после развёртывания. Уникальный индекс по `TournamentId` сохраняется.

Порт исключений переименовывает операцию добавления в операцию добавления или реактивации и получает операцию soft delete активных исключений. PostgreSQL-репозиторий выполняет параметризованные атомарные SQL-команды: upsert реактивирует только soft-deleted строку; update переводит только активные строки в deleted-состояние. Ни `DELETE`, ни `DbSet.Remove` не используются.

Новый application use case использует существующий парсер ввода и возвращает списки возвращённых ID и ID, уже находящихся в пуле. Роутер Telegram ограничивает `/unexclude` личным чатом и существующим authorizer, обрабатывает диалог и показывает безопасное HTML-подтверждение с названиями турниров. `IReadOnlyLookupRepository` возвращает только `IsDeleted == false`, поэтому `/poll`, `/options` и `/excluded` автоматически перестают считать возвращённый турнир исключённым.

## Безопасность и ошибки

Авторизация проверяется до диалога и изменения состояния. Ввод разбирается без SQL-конкатенации; ID передаются только как параметры SQL-команд. Логи содержат лишь Telegram ID, chat ID и количества, без токенов и тел API. API CHGK вызывается только для отображения названий после успешного изменения; его ошибка оставляет нейтральную пометку «название недоступно» и не отменяет уже завершённую операцию.

## Тестирование

Unit-тесты use case покрывают валидный список, атомарный отказ при невалидном токене и уже возвращённые ID. Обновлённые тесты исключения проверяют реактивацию. Тесты состояния диалога покрывают новый enum. Полные форматирование, тесты и аудит NuGet проверяют миграцию, DI и компиляцию.

## Журнал решений

| Решение | Альтернативы | Причина |
| --- | --- | --- |
| `/unexclude` | `/restore`, `/include` | Явно и симметрично описывает отмену `/exclude`. |
| Soft delete через `IsDeleted` + `DeletedAtUtc` | Физическое удаление, `IsActive` | Сохраняет историческую запись и дату возврата, не меняя уникальность. |
| Один record на турнир | Таблица аудита событий | Обеспечивает нужное сохранение данных с минимальным расширением схемы. |
