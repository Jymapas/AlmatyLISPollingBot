# Ограничение запросов к API CHGK

## Понимание задачи

- Бот не должен отправлять более двух запросов в секунду к `api.rating.chgk.info`.
- Лимит должен распространяться на страницы выдачи, запросы турниров по ID и каждую retry-попытку.
- Национальный банк и Telegram не относятся к этому ограничению.

## Допущения

- Текущий сценарий развёртывания — один процесс бота в контейнере, поэтому лимит применяется ко всем CHGK-клиентам этого процесса.
- В распределённом развёртывании общий лимит потребует внешнего координирующего хранилища; такая инфраструктура не входит в текущий объём работ.
- Безопаснее выдерживать равномерный шаг 500 мс без начального burst, чем разрешать короткие всплески.

## Дизайн

`ChgkRequestPacer` — singleton Infrastructure-слоя. Под защищённой критической секцией он назначает ближайшее время фактической отправки, отстоящее от предыдущего на 500 мс, ожидает его и передаёт запрос в транспорт до освобождения следующего слота. Поэтому параллельные вызовы не обходят ограничение. Отмена ожидания может оставить свободное окно, но не увеличивает частоту запросов.

`ChgkRateLimitHandler` вызывает диспетчер непосредственно перед передачей запроса транспортному обработчику. В DI resilience-handler регистрируется раньше него: resilience остаётся внешним обработчиком и при каждой своей попытке повторно вызывает rate-limit handler. Существующая политика retry и её обработка кодов ответов не меняются.

## Безопасность и ошибки

Ожидание принимает `CancellationToken` исходного HTTP-вызова. Обработчик не пишет в лог URL, параметры запросов или ответы API. Лимит не добавляет пользовательского ввода и не меняет разрешённые адреса внешнего API.

## Тестирование

Unit-тесты проверяют резервирование последовательных 500-миллисекундных слотов без реального ожидания. Отдельный тест собирает HTTP pipeline с retry и подтверждает, что все повторные попытки проходят через rate-limit handler. Полный набор тестов, форматирование и аудит NuGet входят в done-критерий.

## Журнал решений

| Решение | Альтернативы | Причина |
| --- | --- | --- |
| Pacer на 500 мс | Token bucket с burst | Равномерный темп проще доказать и не создаёт краткого превышения лимита. |
| DelegatingHandler внутри retry | Ограничивать вызов use case | Handler покрывает pagination, get-by-ID и отдельные retry-attempts. |
| Singleton на процесс | Redis или БД-лимитер | Соответствует текущему развёртыванию без новой внешней зависимости. |
