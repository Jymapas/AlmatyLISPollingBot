# План реализации фичи `/poll`

Ниже зафиксирован план именно для `1 этапа`: довести `/poll` до полностью рабочего сценария в рамках текущего каркаса и `requirements.md`.

## Этап 1. Доменные правила `/poll`

1. Зафиксировать сценарий команды `/poll` в `application` и `domain`.
2. Описать критерии отбора турниров:
   - ближайшая суббота по `Asia/Almaty`
   - `type in {3, 6}`
   - русский язык
   - `ggRating = true`
   - допустимое субботнее окно по `dateStart/dateEnd`
   - исключённые `tournament id`
   - сортировка по `difficultyForecast desc`
   - взять максимум 9 турниров
3. Добавить доменный или прикладной сервис отбора кандидатов и покрыть его тестами.

## Этап 2. Контракты и модель состояния опроса

1. Расширить модель `PollSession`, чтобы хранить все данные для полного цикла:
   - сообщения списка и poll
   - `TelegramPollId`
   - кандидатов с `TournamentId`, названием, порядком в poll
   - время запуска и остановки
2. Доработать `IPollSessionRepository`:
   - получение активной сессии с кандидатами
   - сохранение draft, active, stopped
   - поиск по `TelegramPollId` для будущей обработки обновлений poll
3. Проверить, что `BotSettings` покрывает `stop-time`, `timezone`, `target chat`, `main admin`.

## Этап 3. Telegram application boundary

1. Расширить `IChatBotClient`, так как сейчас он умеет только `SendMainAdminAlertAsync`.
2. Добавить методы:
   - отправка списка турниров в чат
   - создание Telegram poll
   - остановка poll
   - при необходимости отправка сервисных сообщений в чат
3. Вернуть из этих методов transport-agnostic result-модели: `messageId`, `pollId`, `optionCount`.

## Этап 4. Реализация use case `StartPoll`

1. Превратить текущий `CreateDraftAsync` в полноценный orchestration flow:
   - загрузить настройки
   - вычислить `target date`
   - остановить предыдущий активный опрос, если есть
   - запросить турниры из CHGK API
   - отфильтровать и отсортировать кандидатов
   - обработать кейсы `0` и `1` кандидат: не создавать poll, уведомить `main admin`
   - сформировать текст списка
   - отправить список в чат
   - отправить Telegram poll с последним вариантом `"посмотреть результаты"`
   - сохранить `PollSession` как `Active`
   - запланировать автоостановку
2. Отдельно обработать ошибки API и Telegram:
   - логирование
   - alert `main admin`
   - не оставлять сессию в полусломанном состоянии

## Этап 5. Проверки доступа и роутинг

1. Доработать `TelegramUpdateRouter`:
   - реагировать только на нужный чат
   - принимать `/poll` только от администраторов
   - игнорировать остальные чаты и пользователей
2. Подключить чтение админов из БД через lookup/repository.
3. Оставить точку расширения под future private commands, но без смешивания бизнес-логики в worker.

## Этап 6. Инфраструктура Telegram и API

1. Реализовать `IChatBotClient` поверх `Telegram.Bot`.
2. Доработать `ChgkTournamentClient`:
   - корректный маппинг языка
   - устойчивость к ошибкам API
   - нормальные исключения или результаты для application слоя
3. При необходимости добавить retry и timeout policy на инфраструктурном уровне.

## Этап 7. Автоостановка как часть рабочего `/poll`

1. Довести scheduler до реального поведения, так как сейчас там `NoOp`.
2. Сценарий:
   - `/poll` создает задачу на `DefaultPollStopTime`
   - в нужный момент вызывается `StopPoll`
   - poll закрывается в Telegram, статус сессии обновляется в БД
3. Это нужно для критерия “полностью рабочая команда `/poll`”, иначе цикл незавершён.

## Этап 8. Тесты

1. Unit tests:
   - вычисление ближайшей субботы
   - фильтрация и сортировка турниров
   - кейсы `0`, `1`, `2+` кандидатов
   - повторный запуск `/poll` при активной сессии
2. Application tests:
   - happy path публикации списка и poll
   - уведомление `main admin` при `API failure`
   - уведомление при недостатке кандидатов
3. Integration tests по возможности:
   - repository persistence `PollSession`
   - Telegram client contract smoke tests

## Этап 9. Definition of Done для `/poll`

1. Админ в целевом чате вызывает `/poll`.
2. Бот публикует список турниров.
3. Бот публикует `multiple-choice poll` до 10 опций, где последняя опция всегда `"посмотреть результаты"`.
4. При повторном `/poll` старый активный опрос корректно закрывается и заменяется новым.
5. При `0` или `1` кандидате poll не создаётся, `main admin` получает уведомление.
6. Опрос автоматически останавливается по расписанию.
7. Всё состояние сохраняется в PostgreSQL.
